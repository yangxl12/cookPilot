# 接口响应慢排查报告

日期：2026-10-20 · 范围：首页推荐、完整菜谱生成、网页搜索 · 未改动任何业务代码

## 一、结论

> 2026-10-20 15:20 补充：已确认问题环境为「手机 + 生产环境（GitHub Pages）+ 开启梯子 + DeepSeek Flash」。以下数据已加入生产环境手机模拟实测。

1. **首页推荐本身不慢。** 电脑端 2.4s（接口 1.2–2.1s）；生产环境 + 手机模拟 + 4x CPU 降速下 2.2s（接口 1.6s）。提交后 385ms 出现等待气泡，主线程最长任务 151ms。搜索 API 没有参与首页推荐。
2. **生成菜谱慢的真因不是搜索，是校验失败后的全量重生成。** 首次输出几乎必然过不了 `contentSchema` 的枚举校验，触发 1–2 次完整重生成。三道菜复现：3 次/15.4s、2 次/7.3s、2 次/11.2s。手机端每次重试约 +3.4s，踩满 3 次就是 15–25s。
3. **搜索 API 只占 0.3–0.4s（生成总时长的 2–8%），不是当前根因。** 但它串行卡在生成前、最长超时 12s、且没有开关，属于结构性风险，值得加手动开关。
4. **手机 + 梯子是放大器，不是根因。** DeepSeek 是国内服务，梯子若把 `api.deepseek.com` 也代理出境，每次请求多 0.5–1.5s 握手与回程；三次重试累计多 2–5s。建议把该域名设为直连后对比。
5. **非流式输出放大了感知。** 全程只有「正在分析…」「正在生成…」，即使 2s 也显得久。

## 三、根因逐条

### P0：枚举校验失败 → 全量重生成（生成慢的主因）

`src/domain/schema.ts` 把字段限定成了极窄的枚举：

- `cuisine` 只能是「中式」或「西式与日式」
- `ingredients[].group` 只能是「主料」或「调味」

但 `src/services/ai/cooking.ts` 的提示词只给了 `contentExample` 示例，**从未告诉模型这两个字段的可选值**。模型按常识输出「川菜」「意式」「腌料」「碗汁」，`contentSchema.parse()` 直接抛 Zod 错误。

复检审计输出，三次生成的首轮失败原因全部是：

```
cuisine: Invalid option: expected one of "中式"|"西式与日式"
ingredients[1].group: Invalid option: expected one of "主料"|"调味"
```

失败后的处理是 `generate()` 里的循环：把上一次的完整 JSON 塞回对话，再要求「修复以下全部校验错误并重新返回完整 JSON」。也就是说：

- 每次重试都是一次**完整的 6500 max_tokens 请求**；
- 输入还要多带上一次的完整菜谱（+2–3k prompt tokens）；
- 最多 3 次，实际三道菜 100% 至少重试一次。

这就是 7–15s 的主要来源。搜索只占其中 0.3s。

### P1：搜索 API 是串行前置，且无开关

调用点只有两处：

- `src/features/home/Home.tsx:247`：生成菜谱前 `await search(...)`
- `src/features/cooking/Cooking.tsx:177`：制作问答前 `await search(...)`

结构上的问题：

1. **串行**：必须等搜索返回才开始生成，不能省掉这 0.3s，也不能并行。
2. **超时 12s**：`src/services/ai/search.ts:62`。搜索接口一旦抖动/排队，用户会白等最多 12s，然后才静默降级继续生成。这是它唯一可能造成「特别慢」的路径。
3. **没有开关**：生成路径无条件执行；问答路径已有地球按钮（`localStorage['cookpilot-question-search']`），生成路径没有对应开关。
4. **无进度提示**：busy 文案始终是「正在生成 XX…」，用户看不出当前在搜索还是在生成。

### P1：非流式输出放大等待感

`src/services/ai/client.ts:58` 固定 `stream: false`，`max_tokens` 1600–6500。首页推荐 1.2s、生成 4–15s 期间没有任何中间内容，用户只能看转圈。技术上 2s 不算慢，感知上会翻倍。

### P2：手机 + 梯子的放大效应

首页推荐只有一次 `recommend()` 调用，没有搜索、没有额外接口。已确认使用 Flash，排除 Pro 档位的 4.3s。剩余变量：

- **梯子绕路**：`api.deepseek.com` 在国内。手机全局代理会把请求送出境再绕回，单次多 0.5–1.5s；三次重试累计多 2–5s。电脑端 proxy 直连对比无差异（0.34s），说明那边规则已直连。
- **移动网络 RTT**：生产环境实测推荐接口 1618ms，比电脑端 1.2–1.5s 高约 20–35%，属于正常移动网络开销。
- **首次冷启动**：GitHub Pages 首字节 3.2s（链路抖动时可达 20s+），但热启动只有 269ms，日常 PWA 打开不受影响。

### 已排除

| 怀疑点 | 结论 |
| --- | --- |
| 本地代理 7888 | 搜索接口代理/直连均 0.31–0.36s，无差异 |
| IndexedDB 写入 / 渲染阻塞 | 提交后 78ms 出现气泡，0 条 longtask |
| 对话历史长度 | 60 轮（2131 prompt tokens）仅比空对话多 0.3–0.7s |
| 全局搜索页 | 纯本地计算，无网络请求，已用 `useDeferredValue` |
| 保存流程 `commitGeneration` | 单事务，毫秒级；端到端 4.4s 里几乎不占时间 |

## 四、修复建议（按性价比排序，尚未实施）

### 立刻可做（收益最大）

1. **把枚举写进提示词**：在 `contentRules` 明确 `cuisine` 只能是「中式/西式与日式」、`group` 只能是「主料/调味」。预计首轮通过率大幅提升，生成时间从 7–15s 降到 4–6s。
2. **校验前做归一化映射**：把「川菜/鲁菜/意式」映射到「中式/西式与日式」，把「腌料/碗汁/配料/香料」映射到「主料/调味」，映射不了再报错。比让模型重写便宜得多。
3. **放宽到非致命**：`cuisine`、`group` 本质是展示分类，不是业务约束，可改成 `z.string()` + 渲染时兜底。

### 搜索 API 开关（按你的要求）

建议三档，成本从低到高：

- **设置项**：`settings` 里存 `webSearchGeneration: boolean`，默认开；关闭后 `Home.tsx:247` 跳过搜索，直接生成。
- **开发开关**：`import.meta.env.VITE_DISABLE_WEB_SEARCH` 或 URL 参数（`?search=off`），只在开发/排障时用。
- **超时下调**：12s → 4s。搜索实测 0.35s，4s 已经足够宽容；超时即降级，不让用户陪跑。

### 感知优化

4. **改流式**：`stream: true` + 增量解析。首页候选可以先出文字再出卡片；生成时用户能立刻看到 JSON 在长，等待感大幅下降。
5. **分阶段文案**：生成时显示「正在联网核对…」→「正在生成菜谱…」→「正在校验用量…」，让 10s 变得可解释。

## 五、针对你环境的验证与建议

已确认：手机 + 生产环境 + 梯子 + DeepSeek Flash。按这个组合，优先级如下。

### 先做这两步验证（各 1 分钟）

1. **梯子加直连规则**：在 Clash / Surge 里加 `DOMAIN-SUFFIX,deepseek.com,DIRECT`，或在测速时临时关掉梯子，再提交一次。DeepSeek 服务器在国内，代理出境再绕回来是最容易白吃的延迟。如果关掉后明显变快，就是这个原因。
2. **看一次真实数字**：手机连电脑 Safari/Chrome 远程调试，或者用 `chrome://net-export` 抓一次，看 `/chat/completions` 的 TTFB。
   - TTFB 1–2s、总时长 4s → 正常，慢在感知。
   - TTFB 1–2s、总时长 12s+ → 就是本文说的重试。
   - TTFB 6s+ → 链路或服务端排队。

### 然后按性价比改代码

1. **枚举写进提示词 + 校验前归一化**（P0，收益最大）。预计把生成从 7–15s 压到 4–6s，同时省一半 token。
2. **搜索开关 + 超时 4s**（P1）。生成路径加设置项，默认开，可关；`search.ts:62` 的 12s 超时降到 4s。
3. **流式输出 + 分段文案**（P1）。首页候选先出文字，生成时显示「联网核对 → 生成 → 校验」。
4. **首页候选缓存**（P2）。常见菜名可直接命中本地 200 道菜谱，省掉一次推荐请求。

本次数据由 `.local/` 下的临时脚本产生（均已 gitignore，不影响仓库）：
