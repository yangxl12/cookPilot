# CookPilot 正式开发实施方案

分析日期：2026-10-13。

本方案基于现有代码、最终开发说明和本次确认的产品形态：**手机网页 / PWA，先自用和小范围试用**。它是工程实施建议；业务规则仍以 [CookPilot最终开发说明](./CookPilot最终开发说明.md) 为准，页面和交互以根目录 [demo.html](../demo.html) 为准。文中标为“建议”的内容不视为已经变更需求。

## 1. 判断与开发方向

项目已经具备较完整的业务规则、可操作原型和交互测试，可以进入正式开发。现阶段最重要的工作是建立可靠的数据模型和真实 AI 链路，再逐步接回现有页面。

建议在根目录建立正式工程，保留归档和固定 Demo。沿用 React、TypeScript 和现有视觉参数，按业务模块迁移组件；重新实现数据、请求和业务服务。首个交付物应当是一条能实际工作的链路：配置模型 → 推荐选菜 → 完整生成与校验 → 原子保存 → 指南阅读 → 刷新恢复。

目前只需要一个前端工程。先验证浏览器直连模型是否可行，再决定是否需要轻量转发服务。PWA 安装和离线资源缓存放在业务链路稳定之后。

## 2. 当前基础和可复用边界

| 现状 | 工程含义 |
| --- | --- |
| 根目录尚无正式应用工程 | 可以直接按正式数据模型初始化，避免在原型结构上反复迁移 |
| 已有最终开发说明和固定单文件 Demo | 需求与界面已有依据，无需重新设计信息架构 |
| 原型使用 React / TypeScript / Vite | 技术和组件经验可以继承，不必为正式开发更换整套框架 |
| `App.tsx` 共 2248 行，页面、业务、存储和模拟请求集中 | 可提取界面组件，业务逻辑应拆出，避免继续扩充单文件 |
| 原型 `Guide` 同时保存菜谱、版本数字、制作进度和心得 | 与最终说明要求的菜谱版本 / 制作记录分离不同，不能直接作为正式数据库模型 |
| 原型整份状态写入 `localStorage` | 缺少跨实体事务和数据库级去重，应更换正式持久化实现 |
| 推荐、生成、问答和连接测试使用本地规则与延迟 | 正式版需要实现真实网络请求、错误处理、结构校验和取消机制 |
| 有 200 道 Markdown 菜谱资料，原型实际使用 6 道 | 内容结构化和审核是独立工作，资料数量不等于可发布菜谱数量 |

本次已在归档工程运行 `npm run build` 和 `npm test -- --reporter=line`：构建成功，**36 项浏览器测试通过**。这些结果证明原型交互基线可运行，不证明真实模型、多服务商兼容或手机 PWA 已通过验收。本次没有使用真实 Key，也没有执行带凭据的模型连接测试。

建议复用：颜色、字体、间距、卡片布局、弹层、导航交互，以及已有测试中的业务场景。

建议重新实现：存储层、领域类型、模型适配器、生成与保存流程、版本调整、制作记录管理。旧模拟逻辑只留在测试替身或开发环境中。

## 3. 优先澄清的规则及建议处理

### 3.1 实际执行进度如何获取

最终说明要求保留已执行内容，且明确翻卡不代表执行。但原型的 `completed` 主要被读取，并没有建立完整的新执行记录入口；翻卡还会改变 `status`。正式版不能以此判断调料已经下锅或步骤已经完成。

建议保持目前简洁的指南交互：平时浏览不记录执行完成；AI 需要修改流程、又无法确定实际进度时，在问答中做最少的必要确认，例如“鸡肉已经下锅了吗，碗汁是否已加入？”。只有明确确认的信息才进入执行记录。未知状态就保持未知，不能按当前卡片位置补齐。

这不需要增加整餐完成按钮。若以后增加手动步骤完成入口，应作为独立交互决策。

### 3.2 已有菜谱对应哪次制作记录

同一道菜有多个版本、多次制作后，“使用最近保存的版本”和“打开原制作记录”需要一个确定的对应规则。

建议：先按最终说明解析到最近保存的匹配版本，再选择引用该版本的最近一条制作记录，并展示版本及制作日期；点击“查看”始终打开用户点中的记录；“再做一次”始终建立新记录。不要因为其他记录被查看或保存心得，就改变菜谱版本排序。

若匹配版本没有任何制作记录，建议创建一条新记录并明确反馈。此项属于边界处理建议，实施前应写入验收用例。

### 3.3 预置菜谱与 AI 菜谱的复用范围

预置来源和 AI 来源必须保留。用户从菜谱大全打开，不应因此让该菜出现在 AI 菜谱中。预置内容可用于首页候选的身份识别与生成参考，但它不能被标成用户“已有 AI 菜谱”。

预置菜谱按偏好适配时，原始资源保持不变；如需改变内容，保存供本次制作引用的版本快照。对同一结构化内容可复用快照，不因打开一次就复制整套数据。

## 4. 技术方案

| 层次 | 建议 | 用途 |
| --- | --- | --- |
| 页面 | React + TypeScript + Vite | 延续原型技术，维护手机布局和固定 UI |
| 业务状态 | React hooks / reducer，必要时再增加状态库 | 管理页面、弹层和请求状态；持久数据通过仓储读取 |
| 本地数据库 | IndexedDB + Dexie | 按实体保存，支持事务、索引和版本升级 |
| 运行时校验 | Zod 或同类 schema 工具 | 校验模型响应、存储读取和导出格式 |
| 模型连接 | 统一接口适配器 + 原生 fetch | 封装请求、超时、取消、错误及服务商能力差异 |
| 测试 | Vitest + Playwright | 业务不变量测试和用户流程回归 |
| PWA | manifest + service worker | 安装、静态资源缓存和已保存内容离线访问 |

IndexedDB 的事务可以把菜谱、版本和首次制作记录作为一次完整写入；Dexie 提供相关封装及数据库升级机制。模型网络调用应在事务之外完成，校验通过后再进入短事务。[IndexedDB 事务说明](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction)、[Dexie 设计文档](https://dexie.org/docs/Tutorial/Design)。

建议目录按职责保持简单，不引入多包工程：

```text
src/
  app/                 应用初始化、路由和公共布局
  features/
    home/              首页对话与推荐
    recipes/           AI 菜谱与菜谱大全
    cooking/           指南、心得、问答与调整
    settings/          模型与本地数据管理
  domain/              实体、身份解析、用量校验和版本规则
  services/
    ai/                模型适配器、上下文、提示词和响应解析
    cooking/           生成入库、再次制作、确认调整等业务操作
  storage/             数据库、仓储、迁移、导出
  shared/              公共组件、计时工具和样式
  assets/recipes/      已结构化且审核通过的内置菜谱
tests/
  unit/
  e2e/
scripts/               菜谱整理与校验
```

当前应用没有明确的服务端渲染、账户或跨设备同步需求，单一前端工程足以承载首版。选型时安装相互兼容的受支持版本并提交锁文件，不直接照抄归档依赖版本，也不把升级原型依赖当作正式工程建设。

## 5. 浏览器与模型之间的连接

“兼容统一对话接口”只说明请求协议相近，不代表该接口允许浏览器跨域访问。带认证头的跨域请求通常需要服务端正确响应预检；前端代码不能替服务端解除 CORS。[MDN CORS 说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)。

第一阶段应选择实际要用的模型服务，分别验证：HTTPS 页面发起请求、认证、一次短回答、结构化响应、错误和取消。必须在真实浏览器中测，开发代理和命令行请求成功不能代替部署来源验证。真实手机、实际部署来源也要复测。

决策规则：

1. 目标服务允许浏览器直连：静态部署前端，Key 与业务数据在本机保存，请求直接发送到用户配置的模型服务。
2. 目标服务不允许直连：优先明确受支持的服务范围；如果仍需要支持它，再增加受控转发层。
3. 转发层会经手 Key、请求内容和模型响应，即使不落库，也要如实说明；它不是“Key 从未离开浏览器”。公开服务不能提供无需控制的任意地址转发，需要限制可用上游、访问和请求规模。

Key 应和业务实体分开保存，排除导出、普通日志及模型上下文。浏览器本地保存不等于系统安全密钥库，不能把同一来源自动保存解密密钥的方案宣传成充分保护。

首版先确认一套端到端可用的连接，再验证第二套服务和自定义接口的适配边界。UI 可以继续支持多套配置，不必为每个配置单独开发一套业务流程。模型能力不支持时应明确反馈，不能模拟测试成功。

## 6. 数据模型与不变量

| 实体 | 关键内容 |
| --- | --- |
| Recipe | 应用生成的稳定 ID、菜品身份、名称与别名、来源 |
| RecipeVersion | 所属菜谱、不可变内容快照、条件、版本编号、父版本、变更说明及创建时间 |
| CookingSession | 指向具体版本、备菜勾选、浏览位置、明确确认的执行记录、心得及创建时间 |
| Timer | 制作记录 ID、目标类型和稳定目标 ID、状态、截止时间或暂停剩余时长 |
| Conversation / Message | 首页完整消息、候选引用、标题、创建和最后发送时间 |
| CookingQuestion / Message | 绑定制作记录的问答、建议及确认状态，和首页隔离 |
| Preferences / ModelConfig | 偏好、模型非敏感配置、当前模型 ID |
| Credential | 模型 ID 对应的 Key，独立读取与脱敏 |
| GenerationTask | 请求 ID、目标上下文、模型快照、状态、幂等键及结果引用 |

关键不变量：

- 一个菜谱可以有多个版本，一个版本可以被多次制作引用。版本写入后不原地修改。
- 再次制作只建立新制作记录，不重新生成；心得、备菜、执行进度和计时从空开始。
- 确认调整时，新版本和本次制作的版本引用在同一事务更新；其他制作仍指向各自原版本。
- 计时器绑定制作记录及稳定 ID，目标还要区分备菜、烹饪步骤或自定义，避免同名 ID 碰撞。步骤改文案不换 ID。
- 浏览位置独立于执行记录；不因翻卡、计时到点或保存心得写入已完成状态。
- 删除一个制作记录只删其问答、心得和计时；检查其他制作、版本链和有效引用后，才可回收无用版本。
- 菜品身份由应用解析和维护。已知菜品别名可以复用；共享食材只能用于推荐，不能用于判定同一道菜。未知或有歧义的名称不能仅靠模型声称的 ID 强行合并。
- 同一生成任务的结果有唯一约束；同一已解析菜品身份的首次保存还要在数据库事务内查重，覆盖双击、重试和多标签页并发。

库级 `schemaVersion`、模型返回的内容 schema 版本、业务中的菜谱版本分别管理，避免将三者混为一个数字。

## 7. AI 应如何拆分

不使用一段巨型提示词包办全部操作。按业务职责拆成几种能力，共享连接和校验层。

| 能力 | 返回内容与边界 |
| --- | --- |
| 首页对话 / 推荐 | 聊天、澄清或候选摘要；保留相关对话，只生成用户选中的一道完整菜谱 |
| 完整指南生成 | 指定 schema 的菜谱内容，包括食材、备菜、步骤、完成信号和必要限制 |
| 当前制作问答 | 根据明确阶段、实际进度、当前版本、计时和相关问答给操作建议 |
| 调整提案 | 受影响的稳定步骤 ID、结构化变更、原因及依赖；只生成提案，不直接写库 |
| 连接测试 | 使用实际配置发起小请求，验证可用性并返回真实错误 |

推荐和完整生成阶段都要做限制检查。已有版本匹配、选择前查重和保存前查重由应用执行，不能只依赖提示词。

结构化输出仍可能为空、截断或不符合业务语义。以 DeepSeek 为例，官方 JSON Output 文档也说明了截断和空响应的处理注意事项。因此，JSON 可解析只是第一道检查。[DeepSeek JSON Output 文档](https://api-docs.deepseek.com/guides/json_mode/)。

保存前分三层校验：

1. **结构**：必填字段、类型、长度、枚举、数值边界、ID 唯一性、引用存在性。
2. **可执行一致性**：食材用量与备菜、步骤分配一致；先准备再使用；步骤依赖有效；锅具要求及用户限制得到处理。无法量化的“适量”要明确表示，不能假造精确数值。
3. **内容质量**：含义是否可理解、当前步骤的动作与完成信号是否对应。机器可验证的约束由代码完成，其余通过固定评测案例和人工抽查；不能承诺任意模型输出都经过了可靠的语义证明。

数字用量应有一个结构化来源，并由渲染层生成相应显示，避免“文字减半、表格仍是原量”。主料变化不能简单地把所有时间、温度和调料等比例缩放。

建议校验失败时最多做一次有针对性的修复请求，仍失败则保留候选并提示重试。认证错误不自动重试；超时可能已经产生上游费用，不应无限重发。流式文本只用于展示，完整结果校验通过前不能入库。

确认调整前再次检查提案对应的原版本和执行状态。若等待期间已经切换版本或继续执行，应重新评估提案。涉及已经用掉的食材时保留实际记录，信息不足先确认，不用重新生成整道菜来掩盖状态问题。

## 8. 请求、取消与保存可靠性

每个任务绑定发起时的模型配置快照、对话或制作记录 ID、基准版本及任务序号。通过 AbortController 尽力取消网络，再通过上下文校验阻止旧响应提交；仅取消 fetch 不足以证明上游已停止处理。

建议流程：

```text
选择候选
  → 解析菜品身份并查已有记录
  → 建立任务并绑定当前上下文 / 模型
  → 请求模型
  → 解析和完整校验
  → 检查任务是否仍有效
  → 数据库短事务内再次查重
  → 原子写入菜谱、版本、制作记录和任务结果
  → 提交成功后打开指南
```

取消任务的状态变更与结果提交应在应用内有明确顺序；跨标签页时也必须在事务中读取任务状态，避免旧页面的内存标志失效。

保存失败保留结果或编辑草稿，并明确允许重试；只有事务提交成功才能提示已保存。刷新后将尚未完成的任务标记为中断；已经成功保存的结果保留，恢复已有结果，不重复调用生成。

## 9. 本地内容、迁移与 PWA

### 9.1 内置菜谱

200 道资料声明未逐道实做，部分内容依据检索可见信息整理。因此先选 10–20 道覆盖不同做法的菜完成转换与验证，再按同一 schema 扩展全量；这只是开发批次安排，正式首版仍按最终说明完成预置资料整理。

每道保留原编号、来源链接、稳定 ID、分类、别名及内容版本。重点核对食材是否遗漏、用量是否自洽、准备与烹饪如何分段、计时是否只是估计、锅具是否匹配。转换可由脚本或 AI 辅助，审核通过后作为静态资源发布，用户选菜时无需再次从网上采集。

图片先用现有占位方式或已明确可用的素材；归档 README 已指出演示图片发布前需要确认授权或替换，不能默认将其作为正式素材。

### 9.2 本机数据与迁移

浏览器存储默认可能因空间压力或用户清理而丢失；持久化存储请求也不能代替备份。[MDN 存储保留说明](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)。

首版按要求做好脱敏 JSON 导出、保存错误反馈及 schema 升级。JSON 导入恢复是有价值的后续建议，但现有最终说明没有要求，不能作为已承诺功能。

旧 Demo 数据只有在同一来源且可读取时才能直接迁移。直接用文件打开的 Demo、不同端口的开发页与新 HTTPS 域名之间，不能假定正式网页可以读取彼此数据。需要跨来源迁移时，应另行落实一次性转换或导入路径。

迁移应先备份旧原文，再在事务中生成新实体和 ID 映射；保留心得、进度及计时目标，不按“当前版本号”编造已经丢失的历史版本。错误时保留原数据并报告问题，不能自动回到示例数据。

### 9.3 PWA 交付边界

- 缓存应用外壳、字体和内置菜谱；已保存的指南、心得和计时状态从本地数据库读取。
- AI 请求与连接测试仍需要网络，不能离线伪造回答。
- 不缓存带 Key 的模型请求或敏感响应，不将它们放入通用 service worker 缓存。
- 计时按截止时间恢复，暂停保存剩余时长；回前台重新计算，到点不自动推进。
- 做菜过程中不强制刷新更新；更新应用代码时保留兼容的数据库迁移路径。
- 保持正式域名和来源稳定；在 iOS Safari、Android Chrome 及安装后的运行形态分别验证。后台和锁屏提醒仍按最终说明不作保证。

## 10. 开发顺序与完成标准

| 阶段 | 主要产出 | 进入下一阶段的条件 |
| --- | --- | --- |
| A：真实连接验证 | 一套模型的短请求、结构化响应、错误与取消验证；确定直连或转发 | 在目标浏览器和部署来源验证可行；无法取得真实配置时明确标记未验证 |
| B：正式工程与数据底座 | 根目录工程、实体与仓储、schema、事务、空白用户初态 | 版本与制作分离；再次制作、删除引用、保存失败和并发入库通过业务测试 |
| C：第一条真实闭环 | 首页推荐 → 选择 → 完整生成 → 校验 → 入库 → 指南 → 刷新 | 真实模型结果可用；重复提交、取消和保存失败不破坏数据 |
| D：完整制作体验 | 心得、多计时、实际阶段确认、AI 问答、确认调整和版本历史 | 调整只影响本次制作；动作与用量一致；查看位置不会冒充执行 |
| E：补齐正式范围 | 两个菜谱页、全局搜索、历史清理、多模型、导出、旧数据兼容、全量内容整理 | 最终说明的所有业务验收场景可追溯验证 |
| F：PWA 与小范围试用 | 安装、离线已保存内容、更新策略、真实手机回归 | 小范围用户能完成真实做菜；发现的数据与恢复问题已处理 |

界面按阶段迁移，不需要先把全部页面搬完再接模型。每一阶段都保留一个可运行版本，变更 UI 前对照固定 Demo。首个真实闭环稳定之后，再安排更多菜谱和模型兼容。

## 11. 必要测试与首批 AI 评测

原型的浏览器测试可以作为场景清单，但需要按正式实体和真实状态语义改写。模拟连接成功、固定菜谱 ID、默认示例历史和旧存储键等假设不能继续当作正式验收。

优先自动验证高影响业务：生成幂等与取消、版本隔离、删除引用、计时恢复、保存失败、迁移回滚、30 天边界和敏感字段导出过滤。页面流程保留必要的端到端回归，避免为每个简单组件重复写实现细节测试。

模型能力另设固定评测，初批建议覆盖约 30 个案例：明确菜名与别名、共享食材但不同菜、模糊需求、无关聊天、明确主料数量、偏好冲突、锅具不足、准备阶段求助、部分调料已使用、旧版本复用、空 JSON、截断与矛盾内容。

记录生成可用率、校验失败原因、时延和重试次数；不记录 Key，试用诊断也不默认上传完整私人对话。CI 用确定性的模型替身验证业务，真实模型评测在受控环境单独运行，避免成本和输出波动影响每次代码提交。

最后用真实手机验证软键盘、手势、弹层、前台恢复以及安装后运行。桌面浏览器的手机尺寸模拟和现有 36 项通过结果都不能代替这一步。

## 12. 第一批具体任务

1. 将“实际执行确认”和“已有版本对应制作记录”的建议变成明确规则及验收案例。
2. 选定首个实际使用的模型服务，在目标浏览器验证连接，确定部署拓扑。
3. 初始化正式前端工程，提交兼容依赖锁文件及最小构建检查。
4. 定义 Recipe / RecipeVersion / CookingSession / Timer / GenerationTask 与结构化内容 schema。
5. 完成数据库及生成结果提交、再次制作、删除记录三个业务操作。
6. 从 Demo 提取公共弹层、导航、准备卡及步骤卡，接入正式数据读取。
7. 接通推荐和完整生成，完成第一条真实闭环，再进入后续功能。

这些任务的结果应可直接运行和验证。工程规划完成不等于真实模型已打通，页面迁移完成也不等于正式首版已经交付。
